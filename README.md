# Local Research Engine

A lightweight desktop research application that searches the web, extracts source passages, and lets the local model select evidence without writing the quotations itself.

**USP:** displayed quotations are copied from the fetched page text using stored character offsets, then checked against the cached page before they are shown. Each verified quotation links back to its source. The model selects passage IDs; application code constructs the quotation.

## Quick start for users

### Windows

The Windows desktop application and installer pipeline are implemented, but there is not yet a published GitHub Release. Do not download an unofficial installer from an unrelated source.

When a verified release is published:

1. Open the repository's **Releases** page.
2. Download the Windows Setup executable and its SHA-256 checksum file.
3. Compare the installer checksum before running it.
4. The installer is per-user and does not require administrator privileges.
5. Windows SmartScreen may warn because the installer is currently unsigned. The warning is expected, but verify the checksum before choosing to run it.
6. Launch **Local Research** from the Start menu.
7. On first launch, choose the storage location.
8. Open **Models**, install a model deliberately, and select it.
9. Enter a question and choose Simple, Search, or Deep mode.

The first launch does not silently download a model. Model downloads begin only after the user chooses Install.

### Android

There is no Android APK yet. The native Kotlin/Compose application is the next implementation stage after the Windows verification checkpoint. Do not treat the Windows application as an Android build.

## How it works

```text
Question
  -> bounded query planning
  -> search providers
  -> URL validation and page fetching
  -> text extraction and page cache
  -> passage splitting and BM25 ranking
  -> model selects passage IDs
  -> code copies exact page-text slices
  -> hash and offset verification
  -> Sources + verified Quotes + AI Summary
  -> immutable run file
```

The model is not asked to reproduce quotations. It returns passage IDs. The renderer looks up each selected passage, reads the corresponding page text from the local cache, slices the exact stored offsets, and verifies the page hash and text. If the page is missing or verification fails, that quotation is omitted rather than fabricated.

The summary is generated by the selected local model. It is separate from the quotations and can be unavailable if the model does not return a usable answer with valid passage citations.

## Privacy and network behaviour

| Information or operation | Where it goes |
|---|---|
| Prompts and questions | Remain on the device |
| Model inference | Local model runtime or localhost endpoint |
| Settings and project history | Local storage root |
| Downloaded models and page cache | Local storage root |
| Search queries | Sent to the selected search provider |
| Requested webpages and robots.txt | Sent to the corresponding websites |
| Model downloads | Downloaded from the catalog URL only after the user chooses Install |
| Telemetry and analytics | No telemetry or analytics component is included in the current application |

Online research necessarily reveals the search query to the search provider and makes page requests to websites. Those services can observe the network request and its source IP address. This is separate from local model inference: the application does not require a hosted AI model.

The network layer uses bounded retries for selected transient failures and writes redacted diagnostics to the local logs folder. This is not yet a claim that every network failure in the product specification has been tested. See the limitations section and `STATUS.md`.

## Using the desktop application

### Research modes

- **Simple:** one round, one query and up to three pages.
- **Search:** two rounds, up to two queries per round and up to four pages per round.
- **Deep:** four rounds, up to three queries per round and up to five pages per round.

The configured global page and model-call limits still apply. These are bounded workflows, not unlimited crawling.

### Research styles

- **Focused:** sends fewer top-ranked passages to the model.
- **Broad:** sends a wider selection of ranked passages.

### Models

Open the **Models** window from the application menu to:

1. View the catalog and installed models.
2. Install a catalog model after reviewing its details.
3. Resume a partial download when the server supports byte ranges.
4. Verify a catalog SHA-256 value, or explicitly confirm the computed hash when the catalog does not provide one.
5. Select an installed model or remove one.

The current catalog includes a small Q4 GGUF model intended for constrained hardware and a larger Windows-only option. Model quality and speed must be measured on the target device; catalog metadata is not a performance benchmark.

### Projects and history

Research runs are stored as immutable JSON files under the selected storage root, grouped by project. The history view lists saved runs. Opening a saved run re-renders its sources, verified quotations and summary from the stored run and local page cache.

Run files are not edited in place. This is intended to make later folder-based syncing safer, but automatic cross-device sync is not implemented yet.

### CLI

The command-line interface is useful for diagnostics and model/project inspection. The following commands are smoke-tested in CI:

```powershell
.\.venv\Scripts\python.exe -m lre --help
.\.venv\Scripts\python.exe -m lre ask --help
.\.venv\Scripts\python.exe -m lre models list
.\.venv\Scripts\python.exe -m lre projects
.\.venv\Scripts\python.exe -m lre selftest
```

The `ask` command performs research when supplied with a question, a working search connection and an installed/configured local model. CI checks its help/argument parser; it does not run a live research query or download a model.

## Configuration and storage

The shipped configuration is in:

- `config/default.toml`: application, search, fetch, passage, agent and output defaults.
- `config/models.toml`: local model backend profiles and generation limits.
- `config/model_catalog.toml`: downloadable GGUF model metadata.
- `prompts/`: the prompt templates used by the agent.

User overrides are kept separately from shipped defaults. The exact bootstrap location depends on whether the app is running from source, as a portable build, or as an installed per-user application.

The first-run storage picker selects one root for application data. The application separates the content into data, cache, models, logs, temporary files and assets. The user can change the root later; migration verifies copied files and retains the original data.

Typical development storage is under the repository's local storage directory. An installed per-user build initially uses the Windows application-data location unless the user selects another root. A portable build stores its data beside the executable in its portable data directory.

Do not manually move only the model folder while the application is running. Use the storage-location action so configuration and data paths are updated together.

## Project structure

This is a purpose-oriented view of the tracked repository tree. Build outputs and generated runtime data are not application source modules.

```text
.github/workflows/       CI and tagged-release workflows
config/                  Shipped TOML defaults, model profiles and model catalog
docs/decisions/          Architecture decision records
packaging/               PyInstaller and Inno Setup definitions
prompts/                 Agent prompt templates
scripts/                 PowerShell setup, runtime-fetch and build scripts
src/lre/core/            Portable data models and events
src/lre/settings/        Configuration loading, validation and runtime paths
src/lre/search/          Search-provider interfaces and adapters
src/lre/fetch/           URL safety, HTTP handling, extraction and page cache
src/lre/passages/        Passage splitting, ranking, verification and links
src/lre/llm/             Model interfaces, adapters, manager and server lifecycle
src/lre/agent/           Bounded research loop and prompt orchestration
src/lre/storage/         Immutable run-file persistence
src/lre/app/             Service composition, preferences, rendering and self-test
src/lre/ui/              Tk desktop UI and CLI
tests/                   Unit, integration-marked and UI tests
third_party/             Pinned llama.cpp runtime metadata
```

Dependency direction:

1. `core` contains portable data structures and has no UI dependency.
2. Search, fetch and LLM adapters implement narrow interfaces around the core.
3. The agent coordinates those interfaces; the app service wires implementations; UI layers call the app facade.

The UI should not construct search, fetch or model adapters directly. Keep platform-specific implementations replaceable behind the existing interfaces.

## Development

### Prerequisites

- Git.
- Python 3.11.
- Windows PowerShell 5.1 for the documented Windows setup and packaging scripts.
- Inno Setup 6 for a local Windows installer build.
- Android Studio is not required for the current Windows application. It will be used for the planned Android application.

Install Python 3.11 from the official [Python downloads page](https://www.python.org/downloads/). Clone the repository using GitHub's **Code** menu or your preferred Git client.

### Set up on Windows

Run from the repository root:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\setup.ps1
```

The setup script creates a virtual environment, installs the pinned runtime and development dependencies, installs the project in editable mode, and runs the test suite.

### Test and self-test

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m lre selftest
```

The test suite is the primary regression check. The self-test is an offline smoke check intended to work in the packaged application without a model download or live web search.

### Build the Windows package

The CI Windows package job installs Inno Setup, fetches the pinned llama.cpp runtime, builds the one-folder application, runs its frozen self-test, creates the per-user installer and portable ZIP, and writes SHA-256 checksums.

For a local build, after setup and installing Inno Setup 6, run:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\build_windows.ps1
```

The expected outputs are written under `dist/`. The installer is currently unsigned.

### Android build

There is no Android Gradle project or Android CI workflow in the repository yet. Android build instructions will be added with the first Kotlin/Compose milestone. Do not follow generic Android build instructions against this Python-only repository.

## Testing and shared contract

The current Python tests cover passage splitting and verification, ranking, parsing, agent-loop behaviour, fetch/search adapters, storage, settings, model management, network handling and UI helpers.

The CI workflow runs the Python tests and offline self-test on Windows and Ubuntu. It also performs a fresh Windows setup and builds, installs, self-tests and uninstalls the Windows package.

A shared Python/Kotlin contract does not exist yet. It is planned before the Android pipeline port. The contract will define run-file compatibility, text offsets, tokenizer behaviour, ranking order, prompt rendering and result rendering. Python will be the reference implementation and Kotlin will be checked against generated shared test vectors.

## Limitations and known issues

- There is no published GitHub Release artifact at the time of this update.
- The Windows installer is unsigned and may trigger SmartScreen.
- Clean-machine installation has not yet been manually verified.
- Installer size, installed size, cold-start time and target-laptop live research timing have not yet been measured.
- The smallest local model may produce weak query plans or summaries. BM25 fallback is important.
- The complete network failure matrix has not yet been verified. In particular, DNS, TLS, redirects, malformed responses, offline operation, interrupted model downloads and cancellation need broader tests.
- Output truncation detection, finish-reason preservation, code-structure validation and controlled continuation are not implemented.
- The prompt field is currently single-line. Enter submits; Shift+Enter multiline input is not implemented.
- Android, automatic sync, sentence-span selection, tool-call protocol, memory, RAG, profiles and feedback tuning are not implemented.
- The current run format is version 1. The shared contract milestone will introduce the planned version-2 compatibility work.
